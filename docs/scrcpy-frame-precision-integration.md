# scrcpy 帧精度 POC → 正式测速接入方案（讨论稿）

> 状态：**讨论稿**，未实施。按项目纪律，大改动先说明意图与影响面，确认后再动 `server.py`/前端。
> POC 结论见 `docs/scrcpy-frame-precision-progress.md`；macOS 验证清单见 `docs/scrcpy-frame-precision-mac-verify.md`。

## 1. 为什么接（POC 已证明的差距）

| | 现生产（adb 截图轮询） | 接入后（scrcpy 视频流） |
|---|---|---|
| 帧源 | `screencap \| gzip` 一次 ~350ms | 视频流 57.9fps |
| 采样率 | ~3Hz | ~58Hz |
| 单帧成本 | 截图 350ms | 解码 ~3ms + 匹配 ~1.2ms（720 流） |
| 停表粒度 | ~330ms 量化 | ~17ms 量化 |

## 2. 接入目标与原则

1. **不改测速语义**：跳过弹窗（check_skips）、连续确认 + 上升沿抗抖、模板体系全部复用，只换帧源
2. **失败不影响现有测速**：视频流不可用时自动回退 adb 截图轮询（原逻辑原样保留）
3. **前端无感知**：`/api/check_auto` 接口保持兼容；按需求提高轮询频率或改事件驱动
4. **版本锁定**：scrcpy 4.0 协议已验证；升级必须重验（已知边界）

## 3. 推荐方案（B：事件驱动 + 回退）

### 3.1 模块划分

```
server.py 内新增（或独立模块 scrcpy_stream.py，随 server 包分发）：
  ScrcpyStream 类（协议解析自 POC 提取，POC 与生产共用同一份代码）
    - start(serial) / stop()：adb reverse + push server + app_process 启动
    - latest_frame(): 最近解码帧（带 pts/received_at）
    - 后台解码线程：H.264 解码 + 可选每帧匹配（marker/skip）
    - 断流/退出自动恢复（重连退避），异常时标记不可用 → 上层回退截图
```

### 3.2 工作流

- **帧采样循环**：后台线程持续解码。匹配策略（定案）：720 流 + 同分辨率模板 + padding 20 + 阈值 0.85；匹配频率可按需每帧或抽样
- **check_auto 改造**：保持接口与返回字段，内部改为：
  1. 视频流可用 → 读最近帧（亚毫秒），复用现有跳过/marker 判定（连续确认 + 上升沿）
  2. 视频流不可用 → 走现有截图逻辑（原代码路径完整保留，一行不改）
- **停表记录**：命中帧的 `received_at`（主机接收时间）作为停表时间，PTS 作为辅助校验
- **设备切换**：serial 变化 → 停流重启；设备断开 → 标记不可用，回退截图，恢复后自动重连

### 3.3 前端

- 保持轮询 `check_auto`（接口不变）；若要榨干 58Hz 精度，可把轮询间隔降到 100-200ms（纯状态读取，成本极低）
- 测速报告展示"帧源：视频流/截图"字段，便于对比

## 4. 影响面清单（实施前必须逐项确认）

| 项 | 影响 | 处理 |
|---|---|---|
| server.py 热路径 | check_auto 主路径改为读帧，截图路径保留 | 大改动，需回归 29 项测试 + 实机冒烟 |
| 设备 I/O 并发 | 视频流线程与 adb 操作并发（Session 锁外） | 视频流只占用 adb reverse + push（启动时），运行中不占 adb；确认与 SESSION._lock 不冲突 |
| scrcpy-server 分发 | Windows 打包已有 `scrcpy/` extraResources；**Mac 打包缺 scrcpy/adb/ios（已知 H3）** | Mac 接入前必须先补打包资源或文档化依赖 |
| PyAV 分发 | `av` 需进入 python-embed 构建（Windows）与 venv（Mac） | 构建脚本加 av；验证 sourceless 模式 import |
| 生命周期 | 线程启动/停止/异常恢复、进程退出清理（adb reverse --remove、杀 app_process） | POC 的 finally 清理逻辑复用 |
| 兼容 | 老接口/老模板文件格式不变 | 模板路径、缓存结构不动 |
| 性能 | 常驻解码线程 CPU：720 流解码 3ms + 匹配 1.2ms/帧 ≈ 25% 单核（60fps） | 可接受；长跑已证明内存平稳 |
| iOS | 无 scrcpy 视频流，iOS 设备继续走截图轮询 | 按设备类型分支 |

## 5. 建议实施顺序（确认方案后）

1. **代码抽取**：POC 协议解析 + BufferedStream + matcher 提取为可复用模块（`scrcpy_stream.py`），POC 改为 import 它；45 项测试保持通过
2. **ScrcpyStream 落地**：后台线程 + 生命周期 + 重连 + 清理；单元测试（协议/线程/异常路径）
3. **check_auto 双通道**：视频流优先 + 截图回退；回归 29 项测试 + 实机冒烟（含断流回退演练）
4. **前端轮询调整 + 帧源展示**
5. **打包**：av 进 python-embed（Win）；Mac 补资源或文档化（可与 mac 验证并行）
6. 灰度：同事实测对比 adb 截图模式与视频流模式停表差异

## 6. 明确不做（本期）

- 不替代截图模式（保留切换入口）
- 不引入 OBS/录屏式依赖；不用外部高帧率参考做绝对精度验证（后续独立课题）
- 不做 scrcpy 协议升级适配（锁 4.0）

## 7. 决策点

1. 方案 B（事件驱动）是否采纳？还是先做方案 A（轮询读最新帧）灰度？
2. 视频流匹配是否每帧做（58Hz 全匹配）还是抽样（如每 2 帧）？
3. 停表时间以 `received_at`（主机）还是 `pts`（设备编码）为准？
4. Mac 打包资源缺口（H3）是否在本期一并修复？
